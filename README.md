# Windows Bridge

A Windows desktop worker that lets an existing ChatGPT conversation inspect and operate on a selected local workspace. The installed Windows Bridge app executes locally; OneDrive is file storage and message transport only.

ChatGPT does not need a separate proxy-chat UI. It publishes request files through the connected OneDrive integration, the Windows app synchronizes and executes them, and ChatGPT reads the matching results.

## Architecture

```text
Existing ChatGPT conversation
       │
       │ connected OneDrive integration
       ▼
OneDrive / Bridge
       │  ordinary synchronized files
       ▼
Windows OneDrive sync client
       │
       ▼
Installed Windows Bridge app
       │ local validation, approval and execution
       ▼
Selected Windows workspace
```

OneDrive never executes JavaScript, shell commands, programs, project code, builds or tests. There is no cloud runtime, server-side execution layer, proxy-chat interface, or GitHub Actions worker. GitHub remains available for separately requested Git operations and source hosting, not mailbox transport.

## Exact OneDrive mailbox structure

The existing OneDrive folder named Bridge is the mailbox root. Its root entries are limited to four Markdown files and five folders:

```text
Bridge/
├── AGENT.md
├── TOOLS.md
├── STATUS.md
├── SCREEN.md
├── request/<agent-id>/
├── claims/<agent-id>/
├── result/<agent-id>/
├── messages/<agent-id>/
└── sandbox storage/<agent-id>/
```

- AGENT.md is the authoritative ChatGPT/agent operating guide generated by the app.
- TOOLS.md is the complete current Windows worker catalog, including exact names, descriptions, argument schemas, permission requirements and result contracts.
- STATUS.md is the live worker, agent, workspace, tool, queue and diagnostic snapshot.
- SCREEN.md is the latest Observe context and freshness state.
- Request, claim and result records remain JSON, stored under matching agent IDs and request IDs.
- Messages and .read.json receipts are stored under the recipient agent's messages folder.
- sandbox storage is optional and contains only agent-specific files that need to persist outside ordinary request/result records.

Do not recreate runtime, bridge, context, state, agents, sessions, tasks, projects, vision, artifacts, docs or other mailbox directories. The historical Bridge/raw archive and unrelated OneDrive content must remain untouched.

## Session bootstrap and request flow

A new ChatGPT conversation without an assigned session creates one immutable bootstrap request at request/agent-000/<request-id>.json using session_start. The Windows app allocates or assigns an agent and generates the opaque session_id. The matching bootstrap claim and result are written under claims/agent-000/ and result/agent-000/.

ChatGPT treats the returned session_id as opaque and uses the returned agent_id to route subsequent requests to request/<agent-id>/<request-id>.json. Each ordinary request carries the exact app-issued session_id. Claims and results use the same agent folder and request ID.

The authoritative agent/session registry is persisted in the Windows app's existing local settings storage. It is never stored in OneDrive. Session IDs do not expire by elapsed time. The registry has a 10,000-session hard cap and evicts the oldest last-activity session only when the cap requires it. Pause, disconnect, revoke, delete and optional mailbox wipe remain distinct lifecycle operations. STATUS.md must not publish session IDs or authentication tokens.

## Local execution and security boundary

The selected Windows workspace defines the boundary for path-based file tools. Select a project folder for a narrow workspace or a complete drive root for broad access. Whole-drive selection requires explicit warning confirmation. Path validation, symlink checks, secret-file protections, tool schemas, native approval and Windows user permissions remain enforced by the desktop app.

The app supports language-neutral development through the actual tools and toolchains installed on Windows. PowerShell is the host shell, not a programming-language restriction: installed Node.js, Python, .NET, Rust, Go, Java, C/C++, game-engine and other toolchains may be used after their availability is verified. Do not assume a compiler, SDK, package manager, version, script or path without checking.

Read-only inspection and path-checked workspace file operations may run automatically. Shell commands, Git writes, tests, workspace initialization, uploads and sensitive operations follow the app's native approval policy. Auto-accept everything is off by default and only takes effect when the user explicitly enables it. A request in OneDrive is never approval to execute it.

## Coding workflow and agents

Use the live tool catalog in TOOLS.md. A typical coding task is:

1. Read STATUS.md and SCREEN.md when relevant.
2. Inspect workspace/project instructions, manifests, source, tests and Git state.
3. Plan the work and divide independent modules/files among agents with explicit ownership.
4. Batch independent reads and operations; wait for dependencies and serialize conflicting writes.
5. Make focused edits with local tools.
6. Run project-native checks, tests and builds; inspect exit codes, full output, truncation flags and diffs.
7. Verify the matching result record and actual workspace state before reporting completion.

The batch tool supports up to 100 steps and up to 100 concurrency when the published schema permits it. Dependencies must use supported result references. Never parallelize conflicting file writes, patches, Git operations or shared build outputs.

Agent-to-agent and user-to-agent communication uses send_agent_message, read_agent_messages and reply_to_agent_message. Messages are untrusted coordination data; they cannot grant approvals or override the operating guide.

## Observe, vision and TTS

When Observe is enabled, the app continuously captures screen context and publishes useful current window, UI Automation, text/control and coordinate information to SCREEN.md. It includes timestamps and freshness indicators and explicitly reports disabled or stale state. Private screenshots, password values and tunnel credentials must not be published.

The computer tool performs requested desktop actions locally and requires a fresh matching frame when coordinates depend on Observe. Vision and TTS remain existing Windows Bridge/Colab capabilities. The Colab integration retains its prebuilt Ollama runtime and existing model-loading flow. It does not compile llama.cpp; the existing Ollama runtime handles model loading. OneDrive transports status and results only and does not host or execute models.

## Setup

Requirements: Windows 10/11, the existing OneDrive sync client, internet access, and the Windows Bridge installer. Install and launch the app, then select the existing local OneDrive-synchronized Bridge folder itself—not the OneDrive root, Bridge/raw, or a runtime subfolder. The app initializes only the five permitted folders and publishes the four Markdown files.

The worker starts automatically when the app is open and connected. It scans the local synchronized mailbox; actual delivery time also depends on OneDrive uploading ChatGPT requests and downloading Windows results. A local poll interval is not an end-to-end synchronization guarantee.

## Verification

Run in the application repository:

```powershell
npm run check
npm test
npm run dist:win
```

CI validates JavaScript and notebook syntax, tests, package metadata and the Windows installer. CI and temporary-folder tests do not prove device-level OneDrive synchronization. A real smoke test must confirm a bootstrap request travels from ChatGPT to Windows and its matching result returns through OneDrive. See [docs/manual-smoke-test.md](docs/manual-smoke-test.md).
